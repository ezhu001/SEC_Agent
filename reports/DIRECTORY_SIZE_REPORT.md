# SEC_Agent 目录占用检查报告

检查日期：2026-11-04。检查对象：`C:\Users\13466\SEC_Agent`。本次只读取文件信息并新增报告，没有删除或修改环境、缓存、源码、运行记录。

## 结论

这个目录的“9 个多 G”主要来自 **Python 安装缓存、两套虚拟环境，以及开发期间留下的测试产物**，并非项目源码或文字报告变大了。

初次完整扫描共发现 **118,615 个文件**，按各路径的文件长度相加为 **10,034,459,967 bytes**，即 **10.03 GB / 9.35 GiB**。Windows 常用二进制口径显示大小，所以你看到“9 个多 G”与这次扫描相符。扫描没有发现需跳过的链接目录，也没有读取失败记录。

注意：文件长度相加不等于实际占用的磁盘空间。这里存在硬链接，后文另行说明。扫描时新增的几个报告文件会使最终总数略有增加。

其中一个缓存目录的 `torch/version.py` 显示：


## 3. 两套虚拟环境为什么又占约 2.24 GiB

`.venv` 和 `.venv-check` 的 `pyvenv.cfg` 都显示它们由 uv 创建，基于 Python 3.11.13，且不继承系统 site-packages。因此两套环境都要各自有完整依赖。

`IMPLEMENTATION_REPORT.md` 明确记录过：`.venv-check` 是根据锁文件与 editable install 建立的独立干净验证环境，用于检验应用是否脱离 notebook 仍能运行。它有合理的开发用途，但会增加项目目录体积。

每套环境中较大的包包括：

| 包目录 | 每套环境的大致文件长度 |
|---|---:|
| `torch` | 518 MiB |
| `transformers` | 106 MiB |
| `pyarrow` | 89 MiB |
| `pandas` | 72 MiB |
| `sympy` | 72 MiB |

这些包还会产生很多小文件、Python 字节码和前端资源，所以文件数量也很多。该项目的 11 万多个文件，大部分是依赖文件，不是我们手写了这么多程序。

### 当前环境与旧文档存在差别

本次直接读取两套环境的 `torch/version.py`，都得到：

```text
torch 2.15.0+cpu
cuda = None
```

所以本次检查时，这两套环境中安装的是 **CPU 版 torch**。早期 `IMPLEMENTATION_REPORT.md` 中“active .venv 使用 2.7.1+cu128”的表述描述的是当时的开发状态，不能代表现在磁盘上的安装状态。这里没有重新运行模型测试，也没有判断其他目录中的 Python 环境或 Ollama 的设备分配。

这同时解释了为何目录里能并存 CPU 与 CUDA 文件：安装环境发生过变化，但旧下载/解包缓存仍然保留。仅靠文件现状不能恢复每次安装的完整时间线，不过能够确认当前安装与缓存内容的差异。

## 5. 硬链接与实际磁盘占用

已确认至少有如下共享关系：

```text
.venv/Lib/site-packages/torch/lib/torch_cpu.dll
.uv_cache/archive-v0/aQHPErCV22m_xGMA/torch/lib/torch_cpu.dll
```

两者大小都是 309,509,120 bytes，文件身份相同，硬链接计数为 2。它们是两个路径引用同一个底层文件，不能当作两份独立磁盘数据。相应 `.venv-check` 中的同名文件身份不同、链接计数为 1，是独立文件。

因此：

- 一级目录表适合回答“哪个路径下面看起来有多大”。
- 不能把表中大小直接当作删除各目录能释放的空间。
- 删除某个硬链接路径，只要另一条链接还在，就不会释放那份底层数据。
- 去除树内硬链接重复后的统计，也仍不等于磁盘分配大小；压缩、稀疏文件、分配单元以及树外链接会影响实际结果。

完整文件身份检查结果为：

| 口径 | 字节数 | 二进制大小 |
|---|---:|---:|
| 第二轮扫描的路径文件长度合计 | 10,034,472,474 | 9.35 GiB |
| 按树内文件身份去重后的长度合计 | 9,130,864,474 | 8.50 GiB |
| 硬链接导致的重复计数 | 903,608,000 | 861.75 MiB |

第二轮总量与首轮相差约 12 KiB，来自扫描结果文件的新增。约 0.84 GiB 的路径大小属于重复计数；去重后的 **8.50 GiB 仍然只是唯一文件长度合计，并非精确测量的“占用空间”**。上述结果来自完整 `os.stat` 文件身份检查，扫描没有报告访问错误。

## 6. 如果以后要精简，优先检查什么

本次**没有清理任何文件**。以下只是根据检查结果排列的处理方向，不是已经执行的操作，也不是不经核实即可删除的清单。

1. **安装缓存优先。** `.uv_cache` 是最大来源，尤其是历史 CUDA 包。它通常可重新下载，但清理会影响离线重装速度；硬链接也会影响实际释放量。适合在确认后用安装器的缓存管理方式处理。
2. **第二套验证环境其次。** 若暂时不再做独立干净环境复现，可以考虑是否仍需保留 `.venv-check`。它是完整验证环境，不是应用源码；移除后相关复现命令需要重新创建环境。
3. **历史回归产物第三。** 可以按测试轮次归档或择取代表性记录，而不是把整个 `artifacts` 一起处理。这里面既有可重建缓存，也有不可随意丢弃的研究证据。
4. **保留实际运行证据。** `artifacts/runs`、报告引用的源文件、上传原件、必要 fixtures 与文档都很小，而且对期中展示和项目可追溯性有价值。
5. **不要把当前环境里的单个 DLL 当缓存删。** 那可能直接破坏 Python 包。应按完整缓存或环境的边界管理。

这些大目录已在 `.gitignore` 中列为忽略项，包括 `.venv/`、`.venv-check/`、`.uv_cache/` 和 `artifacts/`。忽略规则只影响 Git 跟踪，不会减少本地占用；打包整个文件夹时，也不会自动排除它们。若是给别人展示或传输项目，应区分源码交付与包含完整依赖/历史测试结果的整目录复制。
